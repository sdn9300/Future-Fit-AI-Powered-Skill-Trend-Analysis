### 🟧 Altitude & Heat Adaptation in FIFA World Cups *(current flagship, in active development)*
A sports analytics research project investigating whether **altitude, heat, humidity, and travel fatigue measurably degrade football team performance**, using historical FIFA World Cup data, with forward-looking range-based projections for the **2026 FIFA World Cup**.

- **Data ingestion:** multi-tiered Python pipeline harvesting granular match metrics from **StatsBomb** and **FBref**, combined with environmental parameters from **Meteostat**, **Open-Elevation API**, and geocoded **OpenStreetMap** coordinates to compute historical weather conditions and travel demands.
- **Core statistical model:** Generalized Linear Mixed Model (GLMM) with a Negative Binomial distribution, fit in **R**, to handle overdispersed count data representing team performance markers:

  log(μᵢⱼ) = β₀ + β₁·Altitudeᵢ + β₂·ApparentTemperatureᵢⱼ + β₃·TravelDistanceᵢⱼ + zⱼbⱼ

  where μᵢⱼ is the expected performance outcome of team *i* in match *j*, modeled relative to fixed environmental covariates plus a random intercept vector *bⱼ* capturing team-specific variance.
- **Key architectural decision:** Predictive modeling is deliberately subordinated to inferential/hypothesis-testing modeling. Because ground truth for future tournaments is inherently limited, 2026 outputs are presented as **conditional ranges, not point estimates**, using **leave-one-tournament-out cross-validation** — framed consistently as "projections under historical patterns," never as confident predictions. *(General principle worth reapplying elsewhere: when ground truth is limited, subordinate prediction to inference, and present forecasts as conditional ranges.)*
- **Planning artifacts:** formal hypotheses H1–H5; a 10-phase R data pipeline master plan; an Architecture Design Document with ADRs; a Mission Plan with a risk register and Go/No-Go execution gates (military/operational-style planning); an Evaluation Plan with weighted scoring rubrics; and a 37-scenario Edge Case Registry across six categories.
- **Companion site:** a Next.js 14 portfolio/dashboard site (dark, high-contrast, sports-analytics aesthetic) to display statistical visualizations and range projections, including TypeScript interfaces and venue JSON data.
- **Status:** planning is complete; the R pipeline build phase is next, followed by the companion site deployment.

df.groupby('region')['revenue'].sum()

# Finding index of max within groups

# Label-based lookup with loc
df.loc[best_idx, 'product']

# Multi-condition column assignment with np.select
import numpy as np
conditions = [
    (df['score'] >= 90),
    (df['score'] >= 75) & (df['score'] < 90),
    (df['score'] < 75)
]
choices = ['A', 'B', 'C']
df['grade'] = np.select(conditions, choices, default='F')

# Rounding floats
df['avg_score'] = df['avg_score'].round(2)

# Boolean row filtering
high_scorers = df[df['score'] >= 85]

# Value counts
df['grade'].value_counts()

## 5. Workflow Preferences & Engineering Principles

### Spec-Driven Development (SDD) — non-negotiable
Development is grounded in **Spec-Driven Development**, implemented via the open-source **GitHub Spec Kit** framework. Specifications are the source of truth; code is a secondary implementation detail. This separates the "what" (functional requirements) from the "how" (technical implementation), preventing technical debt, architectural drift, and unstructured AI-assisted development.

**SDD Operational Lifecycle:**
1. **Constitution** — establish guardrails & coding standards (`speckit.constitution`)
2. **Specify** — define user-facing behavior & acceptance criteria (`speckit.specify`)
3. **Plan** — establish technical architecture, schemas, ADRs (`speckit.plan`)
4. **Tasks** — decompose the plan into granular, testable execution blocks (`speckit.tasks`)
5. **Implement** — automated code generation and feature construction (`speckit.implement`)
6. **Validate & Replan** — run automated test suites (`pytest`) and address deviations

**Specification rigor levels:**

| Level | Objective | Where it lives | When used |
|---|---|---|---|
| Spec-First | Early alignment only; not maintained post-generation | Initial prompt / disposable doc | Rapid, low-complexity prototyping |
| Spec-Anchored | Specification evolves with the codebase as a living reference | Repository `/docs` or `/specs` | **Primary operational standard** for flagship systems and statistical pipelines |
| Spec-as-Source | Code generated directly from spec; humans don't edit code files | Config/DSL file + automated compiler | Isolated, low-criticality automation tasks only (non-deterministic risk otherwise) |

Soumyadeep operates primarily in the **spec-anchored** mode: specs are version-controlled repository assets, verified through automated integration tests, not disposable prompt inputs.

### Core engineering/working principles (recurring defaults)
1. **No code before a spec exists.** Discovery → Design → Architecture → Code.
2. **Documentation explains "why," not just "what."** Every architectural decision carries its rationale (ADRs).
3. **Predictive modeling is subordinate to inferential modeling** when ground truth is limited — forecasts as ranges with cross-validation, not point estimates.
4. **Military/operational framing for planning** — mission phases, risk registers, Go/No-Go gates. A genuine preference, not decoration.
5. **Debugging is root-cause-first.** If an error occurs, the AI/collaborator must isolate the actual underlying cause, explain it in clear technical terms, and update test suites to prevent regressions — never apply quick fixes or surface-level patches.
6. **Iterative, progressively deeper deliverables.** Comfortable working in layers (problem statement → architecture → implementation → evaluation → hardening), often via simple "Continue" prompts.
7. **Elaborate, highly organized documentation is a feature, not a burden.** Long-form specs, ADRs, schema contracts, registries are preferred over terse output.
8. **Balance spec detail with execution cost** — to avoid over-engineering, the effort spent refining specs should not exceed the cost of fixing the errors it prevents.

### How collaborators/AI assistants are expected to operate
- Act less like a chatbot, more like a senior advisor, systems engineer, architect, researcher, and instructor
- Verify design decisions against the specification before writing code
- Start with structure before implementation; explain rationale, not only results
- Treat complex work as a system, not a single answer
- Be direct when something is weak, unclear, or not credible
- Prioritize what is most useful for employability and long-term growth

### Preferred workflow pattern
1. Define the problem clearly
2. Identify constraints
3. Design the structure
4. Propose an architecture or plan
5. Implement or rewrite

7. Refine for clarity, credibility, and impact
